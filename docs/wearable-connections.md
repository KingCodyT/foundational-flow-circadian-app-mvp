# Optional wearable connections

## MVP scope

Repository inspection found no wearable adapters, native health bridges, OAuth routes, credentials, or wearable import pipeline. The new settings live at **You → Connections → Wearables** (`/profile#wearables`). The disconnected screen has a Connect a wearable button and is independent of phone notification preferences. The complete onboarding, schedule, phone-context, reminder, and minimal-input experience remains available without a device.

The production provider registry is deliberately empty. Connect a wearable opens a coming-soon panel without changing connection state, inventing providers, creating a sync timestamp, or importing observations. The former enable checkbox has been removed. Old saved opt-in values do not establish a connection. No provider names are advertised until a real adapter is configured.

Connection controls require a configured provider and a session verified in the current app session. Connecting and failed/unverified attempts have no sharing, management, disconnect, last-sync, or deletion controls. Connected and syncing sessions show management and sharing; a previously verified connection that needs attention can still be managed. Delete imported wearable data appears only on a verified connection with actual imported observations, never merely because a last-sync timestamp exists. Disconnected users with retained data see an honest retained-data notice and the connection entry point, with no connected-only controls.

`lib/wearables/connection.ts` defines the provider contract, connection lifecycle, consent gates, provenance, and data controls. `CircadianProvider` persists this separate state alongside the existing local app state. No credentials belong in this state. No wearable data is currently consumed by coaching, and no provider calls occur in this MVP.

## Lifecycle and data control contract

- A real adapter must implement connect, session verification, granular sharing, sync, disconnect/revocation, and deletion of app-held imports. Register it only after wiring and testing these operations in the settings UI and a sync coordinator; adding a registry entry alone is not an integration.
- Dispatch `connecting` only for a real configured adapter. After authorization, dispatch `verified` with the current revision and the provider's actual capabilities and grants. Only registered providers can establish a connected state. Hydration requires re-verification; persisted status never proves a live connection.
- Sync captures the current revision and provider ID. Dispatch `syncing`, then `synced` only after a successful request. An empty response is allowed and is not a user failure. Show `attention` for connection problems, without penalizing the user. Preserve the actual last successful sync time, not the last attempt.
- Read only the intersection of user-selected, provider-supported, and provider-granted categories. Import validation repeats those gates, validates timestamps and finite values, checks provider ownership, and deduplicates record IDs. Temperature and HRV measures must retain their native metric/unit; do not equate different methods or device capabilities.
- Disable, disconnect, sharing changes, and deletion increment a revision so late sync responses cannot restore deleted or unshared data. A future sync coordinator must also abort requests and stop webhooks/jobs at the backend. Turning a category off purges its local imported records; a future adapter must enforce the equivalent server-side purge and permission changes.
- Disconnect retains app-held imported history until explicit deletion, but makes it unavailable as supporting evidence. The current UI cannot revoke an unconfigured provider: it can only remove local connection metadata. A future integration must distinguish remote revocation success from local disconnection.
- The state layer can remove local observations and last-sync metadata even while disabled, but this settings interface shows deletion only for a verified connection with imported records, per the connected-only UI rule. It never changes schedule anchors, meal history, answers, reminder preferences, or the provider's own source records. Future backend storage must implement the same deletion guarantee, including derived caches, and report partial failures. While still connected, later syncs may import again; turning the connection off prevents this.
- Before real health imports ship, select authenticated per-user storage, retention limits, secure transport, protected token storage, pagination/cursors, rate-limit handling, retry behavior, and account deletion propagation. The current local preferences store is not a production credential vault or a completed health-data storage design.

## Coaching invariants

Wearable observations are labeled `wearable_inference`, distinct from user-entered information. A device reading is supporting evidence, not truth or proof of compliance. The evidence accessor excludes low/unknown-quality observations and disabled/ungranted/unsupported categories. It does not write to any coaching state.

A future coaching integration may increase confidence only with multiple independent, corroborating signals and explicit quality/freshness rules. Preserve `independentSourceId` so the same underlying sensor copied through Apple Health and a vendor API does not count twice. Do not automatically replace the primary target because of one reading. Missing, contradictory, stale, or low-quality data must never reduce user standing or create a task. User-entered wake time, bedtime, meal timing, and constraints remain authoritative until the user edits them. Constraint is not noncompliance. Future inferred summaries must be labeled as estimates, show their provenance, and stay separate from saved schedule fields.

## Provider-dependent implementation work

These are integration requirements, not a promise that any provider supports all five categories. Recheck provider approvals, terms, scopes, and device/account support when implementation begins.

| Provider | Required work before enabling connection |
| --- | --- |
| Apple Health | Build an iOS native HealthKit bridge/companion; configure the HealthKit capability/entitlement and purpose descriptions; request read authorization for individual types, check availability, map records and sources, and handle revocation and background updates. This web app alone cannot invoke the native HealthKit authorization flow. See [HealthKit entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.healthkit) and [authorization](https://developer.apple.com/documentation/HealthKit/authorizing-access-to-health-data). |
| Health Connect | Build an Android bridge using the Health Connect SDK; check availability, declare required data-type permissions and Play Console access, request granular permissions, and implement change reads/deletion and optional background access. See [get started](https://developer.android.com/health-and-fitness/health-connect/get-started) and [availability](https://developer.android.com/health-and-fitness/health-connect/availability). |
| Fitbit / Google Health | Register the appropriate developer application, configure OAuth consent and server-side credential handling, map approved data scopes, implement refresh/revocation and incremental imports. Google now documents the Google Health API as the next generation of Fitbit Web API; choose the supported path at integration time. See [Google Health API](https://developers.google.com/health), [Cloud/OAuth setup](https://developers.google.com/health/setup), and [Fitbit API reference](https://dev.fitbit.com/build/reference/web-api/explore/). |
| Garmin | Apply to the Garmin Connect Developer Program and obtain Health API approval/evaluation access. Implement its authorized user connection and delivery/import flow, map supported metrics, handle revocation and deletion, and validate real device records. See [Garmin Health API](https://developer.garmin.com/gc-developer-program/health-api/). |
| Oura | Register an OAuth2 application, obtain user consent, implement secure token handling and the approved API endpoints, and check actual scope/device/account capabilities. Add incremental sync, revocation and deletion behavior. See [Oura getting started](https://cloud.ouraring.com/docs/) and [authentication](https://cloud.ouraring.com/docs/authentication). |
| Other providers | Implement the same adapter contract with real authorization, capability discovery, provenance, quality handling, consent changes, revocation, and deletion. Do not add a provider based only on its name or a claimed data category. |

## Validation

Unit tests cover default-off state, unavailable adapters, capability/consent filtering, valid connection states, sync timestamps, low-quality evidence exclusion, deletion, stale response rejection, and independent preferences. Component state-matrix tests cover disconnected, connecting, connected, syncing, failed/unverified, verified-needs-attention, retained-data, and empty-import states. Browser smoke covers the real disconnected desktop/mobile experience, coming-soon messaging, legacy preference migration, retained-data notices, and unchanged notifications/schedule/Today behavior. Test observations are explicit fixtures confined to tests; the application generates none.
